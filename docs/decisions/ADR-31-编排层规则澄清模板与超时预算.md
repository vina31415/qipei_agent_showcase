# ADR-31：编排层规则、澄清与回答模板 + LLM 超时预算

- 状态：已接受
- 日期：2026-07-21

## 上下文
需确定编排层的意图、参数抽取规则、澄清策略、回答模板，并解决 llm_timeout=10s 与端到端 P95≤3s 的矛盾。

## 决策

### 意图列表（M1 三种）
`oe_query`（OE 号 → SKU）/ `fitment_query`（车型 → SKU）/ `lead_time_query`（交期查询）

### 参数抽取（规则优先，命中才不调 LLM）
- OE 号：正则识别（字母数字 + 分隔符）→ 归一化匹配
- 车型：品牌 / 车系 / 车型 + 4 位年份数字
- 数量：数字 + 单位（件/套）

### LLM 兜底
规则 miss 时才用豆包 function calling 抽意图 + 参数（触发 llm_timeout）。

### 澄清策略（追问条件）
- OE 无结果 → 提示未找到 → 触发兜底 → 仍无 → 建议宽松匹配或换车型查
- 车型缺年份 → 追问年份
- 多 SKU → 直接返回列表，不追问

### 回答模板
固定结构：SKU 列表 + 车型 + 图片 + 库存 + 价格 + 交期 + risk 标签（ADR-13 模板拼接，不调 LLM）。

### 超时预算（P95 口径澄清）
- 规则路径目标 < 1s（纯正则，不调 LLM）
- **规则命中率 ≥ 95%**（新增指标，P95≤3s 成立的前提）
- LLM 兜底仅在 ≤5% 请求触发，`llm_timeout` 收紧到 **2s**（原 10s），**超时即降级到规则模板回答**（「无法自动识别，请换种说法或人工查询」）
- 端到端检索不实时打金蝶/PIM（全读 MySQL 主数据；金蝶/PIM 只在 ETL 与兜底触发）
- **P95 口径**：统计全部请求（含 LLM 兜底）。规则路径 <1s、LLM 兜底 ≤2s（超时降级），故任何请求 ≤2s，P95≤3s 无条件成立。
- **联合验收拆两条独立指标**：① 规则命中率 ≥95%（意图/抽参测试集，ADR-38）；② P95≤3s（端到端全量，含 LLM 兜底）。两者独立，无耦合。

## 理由
- 规则优先保命中率与速度，P95 主体由规则路径决定；LLM 只兜底少数 miss，其慢耗时不影响 P95。
- 澄清策略避免无谓多轮，多 SKU 直接返回列表。

## 后果
- `intent.py` / `param_extract.py` 实现规则抽取 + LLM 兜底；`answer_render.py` 按模板渲染。
- 「规则命中率 ≥ 95%」纳入 spec §4 验收标准与测试场景。
- `llm_timeout` 由 10s 改 5s（同步 ADR-22 / ADR-23 / spec §3.6 / §5）。

---

## 作者批注：为什么做这个决策

这条 ADR 解决的是一个硬矛盾：LLM 抽参天然要好几秒，而业务要求 P95≤3s。解法是指标拆解——把"快"拆成"95% 的请求走纯正则规则（<1s），5% 的 miss 才走 LLM（预算 2s，超时降级模板）"，这样 P95≤3s 无条件成立，不靠运气。配套地新增"规则命中率≥95%"作为独立验收指标：它是 P95 成立的前提，必须分开度量、分开验收。用确定性预算管理不确定性，是我从传统性能工程带过来的思路。
