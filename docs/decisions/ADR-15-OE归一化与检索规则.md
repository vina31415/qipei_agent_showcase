# ADR-15：OE 归一化与检索规则（v2 定稿）

- 状态：已接受
- 日期：2026-07-16

## 上下文
ADR-05 定义了 OE 归一化方向。业务方提供 26 条真实样本 + 内部约定后确认：OE 号大量字母数字混合、无统一固定位宽、欧系常见末尾版本后缀字母；存在「带前导零 / 丢前导零」混录（博世等为重灾区）。故弃「补零」，改「确定性归一化 + 精确优先 + 可选宽松」。v2 修正前缀清单大小写、纯 0 处理、宽松匹配标注与多 SKU 排序。

## 决策

### 归一化流水线（规则落配置表，不硬编码）
1. trim 首尾空白
2. 统一大写
3. 去前缀（按下放大写清单、**长度降序**匹配）
4. 去所有非字母数字字符（空格、`-`、`/`、`.`、`_`、`#`、`:`、`°` 等），只保留 `[A-Z0-9]`
5. 纯数字 OE 额外去前导零（`0986479012` → `986479012`）；含字母 OE 不动前导零
6. 不做位宽补零
7. 去前导零后为空串（如全 0 的 `000`）→ 标记**无效 OE**，跳过索引、不参与检索（原始值保留入库留痕）

### 前缀清单（全部大写，含标点边界）
`REF.NO.` / `OEM` / `OE` / `REF` / `NO.` / `N°` / `OE#` / `OEM#`
> 匹配按清单项长度降序（OEM 先于 OE）。**无标点后缀的前缀（`OE` / `OEM` / `REF`）匹配后必须紧跟非字母数字字符或字符串结尾**（防 `OEM123` 误删）；含标点前缀（`REF.NO.` / `NO.` / `N°` / `OE#` / `OEM#`）自带边界直接匹配。

### 检索匹配模式（两种，业务员可切换）
1. **精确匹配（默认）**：`oe_normalized` 全等。
2. **宽松匹配（可选开关）**：剥离末尾连续字母（`1K0615301AA` → 基号 `1K0615301`），返回同基号结果。
   - 仅用于兜底匹配；返回结果须**同时展示原始完整 OE 号**，并标注【宽松匹配，已剔除末尾后缀字母，请业务员复核适配性】；不得用裁剪后的 OE 作为标准 OE 本体。
   - 红线：`6Q0820803C` 与 `6Q0820803` 是两个不同 OE，精确模式不得混。

### 多 SKU 排序与标签
一个 OE 命中多个 SKU 时：**原厂 OE 优先、REF 靠后**；同类型按 `sku_code` 升序。返回带标签区分【原厂 OE】【REF 参考号】。

### 原厂 OE / 参考 REF 区分
PIM 字段 `oeRemark` 区分【原厂 OE / 参考 REF】：含「REF」→ REF，否则 → 原厂，映射到 `oe_type`。

## 理由
- 无固定位宽 → 补零会碰撞不同零件，弃用；改确定性归一化。
- 前导零混录经业务方确认，纯数字 OE 去前导零消除同件不同录的漏配。
- 前缀清单统一大写 + 长度降序，消除大小写（Ref.No./ref.no.）匹配失效与 OE/OEM 前缀误伤。
- 版本后缀字母是真实差异维度，精确优先；宽松匹配显式标注 + 人工复核，风险可控。

## 后果
- `oe_mapping` 表增加 `oe_base`（去末尾字母后的基号）索引列供宽松匹配；`oe_type`（原厂/REF）纳入筛选与排序。
- 前缀清单、分隔符、去前导零、无效 OE 规则落 `config/oe_normalize.yaml`。
- 宽松匹配开关在渠道层（UI）暴露；宽松结果必带标注。
- 宽松模式为启发式，对部分日韩系编号可能过度放宽；因必带标注 + 人工复核，风险可控。

---

## 作者批注：为什么做这个决策

OE 号的脏是这个行业的老大难：同一个刹车片有 `0986479012`、`0 986 479 012`、`REF.NO. 9864790 12` 等十几种写法，供应商报价单、客户口头、旧系统里各一套。归一化规则前后迭代了三版（见 change_note），最难的是前缀边界的误判：`OEM123` 里的 "OE" 不是前缀，不能删——靠"无标点前缀必须紧跟非字母数字或结尾"这条边界规则解决。26 个样本是和业务方逐条核对后固化的，它们既是规则的正确性依据，也是回归测试的断言来源。规则全部读 yaml 配置而非硬编码，因为前缀清单一定会随业务增长。
