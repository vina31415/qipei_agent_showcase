# 复盘：从 v1 到 v2 —— 一次"本地全绿、云端全红"引发的重构

> 这不是项目的黑历史，而是这个项目最有价值的部分之一：第一版交付后，我在干净环境验证时发现了系统性问题，没有打补丁，而是把教训沉淀为 5 条工程约定（ADR-39~43），按更新后的 spec 做了 v2 重构。本文如实记录这个过程。

## 背景

v1 在开发机上交付：devlog 显示 pytest 全绿、ruff 零告警，看似达标。但当我把它推到 CI（干净 Ubuntu 容器、无内网、无密钥）验证时，连续暴露四类问题；随后在本机复跑还发现了第五类。

## 暴露的问题与根因

| # | 现象 | 根因 | 教训 → 沉淀为 |
|---|---|---|---|
| 1 | CI 上 18 个集成层测试全灭 | `pyproject.toml` 依赖清单里**没有 `pytest-asyncio`**，异步测试靠开发机全局环境"恰好装了"才跑得动 | 依赖必须显式声明 → ADR-43（版本下限入 spec） |
| 2 | 39 个测试 FileNotFoundError（config/*.yaml） | flat 布局下代码、测试、配置互相用 `parent.parent` 相对寻路，目录一变动全断 | 结构耦合 → ADR-42（src layout 单包 + hatchling，config 不入包） |
| 3 | 干净环境跑不了任何测试 | 外部依赖（LLM/网络/文件）直接在函数内实例化，测试只能依赖真实服务或全局 patch | 可测性靠运气 → ADR-41（依赖注入：外部依赖构造函数/参数注入） |
| 4 | ruff 在 CI 报 12 个告警而本机是零 | 本机和 CI 的 ruff 版本/环境不同，"零告警"只在特定环境成立 | 环境漂移 → ADR-39（CI 进 DoD：可提交的 ci.yml 本身是交付物） |
| 5 | 本机跑测试内存归零、风扇狂转、VSCode 卡死 | 一个测试写了自指函数，数据无限累积 | 防 hang 防泄漏 → ADR-40（分层 mock 策略）+ CI 加超时保险 |

## 处置方式：不打补丁，改 spec

两个问题摆在面前：逐项修 bug 很快，但同样的问题会在下一个项目重演。我选择回到 spec 层：

1. 把五条教训写成 **ADR-39~43**（上下文/决策/理由/后果），作为工程约定冻结；
2. spec v2 增量更新（plan 头部有完整的 v1→v2 变更映射表），由规划 Agent 做增量计划而非推翻重来；
3. 按新 spec 执行 v2：src layout 重构、依赖注入改造、测试按 ADR-40 分层 mock 重写、ci.yml 作为 P1-1 的交付物第一时间进仓库；
4. 结果：CI 与本机双端全绿（298 passed），能力层/集成层行覆盖 ≥80% 达标。

## 我带走了什么

- **"开发机绿"不等于"可交付"**：只有无密钥、干净环境的 CI 绿才是可复现的绿。CI 必须从第一天就在仓库里，而不是最后补。
- **可测性是设计出来的，不是测出来的**：ADR-41 的依赖注入约束让"换一个 LLM/换一套配置/换一个时钟"变成传参问题，测试不再需要撬动全局状态。
- **返工的正确姿势是把教训上移一层**：bug 修在代码层，复发在项目层；修在 spec/ADR 层，复发在别的项目也被挡住——这也是这套 spec-driven 流程本身的胜利：v1 的失败经验能干净地进 v2 的决策文档。
